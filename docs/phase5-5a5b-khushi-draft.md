## 0. Ownership split

**Namitha owns (model layer):**
- `model_id`, `model_version` (source value), `model_type`
- Probability capability signaling: `supports_probability` (adapter-internal only, never serialized in a shared schema)
- `predict_batch()`'s optional adapter/injection mechanism — existing no-adapter callers preserve current LR behavior, prediction semantics, probabilities, instance IDs, feature matrix unchanged
- Raises `ProbabilityCapabilityUnavailable(Exception)` when a probability-dependent operation (e.g. ROC-AUC) is requested but the adapter can't provide probabilities
- Internal, non-serialized access to the fitted model/artifact and explainability background/reference data
- `explainer_type` stays internal to explainability (Manas selects Linear vs Tree from `model_type`/the fitted estimator) — not part of the shared contract

**Khushi owns (API/orchestration layer):**
- `assurance_run_id` creation and propagation — minted once in `build_assurance_result()`, never crosses into the model layer, attached to results *after* model-layer functions return
- Combining model identity + run identity into `AssuranceRunContext`
- API/schema placement and validation
- Catching `ProbabilityCapabilityUnavailable` and mapping it to `ModelMetrics.roc_auc_status = "unavailable_no_probabilities"`
- `NOT_COMPARABLE` handling where it intersects capability failures

## PART A — Namitha's Model-Facing Design (her formal write-up, 2026-09-13)

### A0. Existing semantics — explicitly frozen

- `0 = GOOD / favorable / lower risk`, `1 = BAD / unfavorable / higher risk`
- Probability means `P(class 1) = P(BAD)`
- Existing `instance_id` generation/preservation unchanged
- Existing raw 20-feature schema/order unchanged for current German Credit models

### A1. Model identity

The model layer provides a stable logical `model_id`, separate from model version and assurance-run identity:
- Current LR: `"german-credit-logistic-regression"`
- Future RF: `"german-credit-random-forest"`
- `model_id` remains stable across retraining and assurance runs
- `model_metadata.version` remains the single source of truth for model version — not renamed or duplicated
- `assurance_run_id` is NOT owned or generated by the model layer — remains an orchestration-level concept entirely

### A2. Probability capability

Probability support is a model/adapter capability, not a shared serialized contract field:
- `supports_probability` stays internal to the adapter — NOT added to `ModelMetadata`, `model_metadata`, or any API schema
- LR and RF both require/support `predict_proba()` in Phase 5
- Probability values must never be fabricated for an adapter that doesn't support them

### A3. Probability-dependent evaluation — model layer owns the guard

- Before computing ROC-AUC, the model layer verifies probability capability
- If an operation requires probabilities and the adapter can't provide them, the model layer raises `ProbabilityCapabilityUnavailable` — before calling `roc_auc_score()` or hitting an opaque sklearn failure
- API/orchestration owns catching this and mapping it to `roc_auc_status`

### A4. Internal/non-serialized model capabilities

The adapter may provide internal access to: the fitted model/Pipeline or artifact, expected feature names/schema, explainability background/reference data. **None of these are serialized into `ModelResult` or the public assurance contract.**

`explainer_type` is NOT part of the model adapter/shared contract — Explainability (Manas) owns selecting Linear vs. Tree explainers using the available model identity/type and fitted estimator.

### A5. Model Adapter design (5B)

One model-facing boundary so downstream assurance code doesn't need separate LR/RF-specific interfaces. The adapter owns: `model_id`, `model_version`, `model_type`, expected feature names/schema, prediction execution, probability capability, internal fitted-model/artifact access, internal background/reference-data access.

Conceptual interface (exact class/method names finalized during implementation — these describe required responsibilities, not frozen implementation details):
```python
model_id
model_version
model_type
feature_names
supports_probability

predict(X)
predict_proba(X)
load_fitted_model()       # or equivalent internal accessor
background_data()         # or equivalent internal accessor
```

### A6. `predict_batch()` integration

The model layer owns making `predict_batch()` adapter-aware:
```python
predict_batch(feature_matrix=None, *, adapter=None)
```
Exact signature frozen jointly before implementation. When no adapter is supplied, current LR behavior remains the default — existing callers retain identical prediction semantics/values, probability semantics, `instance_ids` behavior/alignment, `feature_matrix` content/order, and meaning of all existing output fields. Phase 5 identity additions are additive only.

### A7. LR conformance

Existing LR becomes the default adapter-backed model, unchanged semantics/preprocessing/target polarity/behavior. Exposes: `model_id = "german-credit-logistic-regression"`, existing model version `0.1.0`, `model_type = "logistic_regression"`, probability support, existing feature schema, fitted pipeline/artifact access, required explainability reference/background access.

### A8. Future RF conformance (5C)

RF must implement the same adapter boundary, not a separate downstream contract: `model_id = "german-credit-random-forest"`, its own model version, `model_type = "random_forest"`, same target polarity, probabilities representing `P(BAD)`, `predict()`/`predict_proba()`, compatible feature-schema handling, fitted artifact + explainability background/reference access.

Downstream consumers receive model identity through the assurance context, never LR/RF-specific branches in the shared model contract.

### A9. Full ownership boundary (Namitha's formal statement)

**Namitha / model layer:** model identity source, adapter boundary, `predict_batch()` injection, probability capability checks, `ProbabilityCapabilityUnavailable`, fitted artifact/background access, LR/RF model conformance.

**Khushi / API + orchestration:** `AssuranceRunContext`, `assurance_run_id` creation/propagation, schema/API validation, assurance envelopes, `roc_auc_status` mapping, `NOT_COMPARABLE` API behavior, downstream integration.

**Manas / Explainability:** Linear vs. Tree explainer selection, model-specific SHAP handling.

**No implementation is included in this design section. Implementation begins only after the combined 5A/5B document is reviewed/frozen.**

## PART B — Khushi's API/Integration Design

### B1. Contract serialization / schema (new, additive — 5A)

Existing result schemas (`FairnessResult`, `DriftResult`, `ModelResult`, etc.) are **not modified**. A new wrapping envelope carries identity:

```python
class AssuranceRunContext(BaseModel):
    """Identity envelope threaded through one assurance run. New (5A)."""
    model_id: str
    model_version: str
    assurance_run_id: str
    adapter_id: Optional[str] = None

class FairnessAssuranceEnvelope(BaseModel):
    context: AssuranceRunContext
    result: FairnessResult          # existing, unmodified

class DriftAssuranceEnvelope(BaseModel):
    context: AssuranceRunContext
    dataset_id: str
    dataset_version: Optional[str] = None
    feature_space: str
    result: DriftResult             # existing, unmodified
```

All identity fields are **required, no default** — a missing value fails pydantic validation immediately, following the exact precedent already shipped in this codebase (`ModelResult.instance_ids: list[str]`, no `Optional`).

**Placement and sourcing, resolved with Namitha:**
- `model_id`/`model_version` live **top-level on `AssuranceRunContext`, not nested under `model_metadata`** — forced by the schema, since `FairnessResult`/`DriftResult` have no `model_metadata` field at all today.
- `model_version` is **not a new independent field** — populated at envelope-construction time in `orchestration.py` by reading the existing `model_metadata.version`.
- `assurance_run_id` does **not** cross the model boundary. Minted by `build_assurance_result()`, attached to results after model-layer functions return.

### B2. `ModelMetrics.roc_auc` — capability-dependent

`roc_auc` is the **only** metric in `ModelMetrics` that hard-depends on `predict_proba()` — `accuracy`/`precision`/`recall`/`f1` all come from `model.predict()` (hard labels) alone. Confirmed by reading `evaluate()`'s actual code.

```python
class ModelMetrics(BaseModel):
    accuracy: float
    precision: float
    recall: float
    f1: float
    roc_auc: Optional[float] = None
    roc_auc_status: Literal["computed", "unavailable_no_probabilities"] = "computed"
    n_test_samples: int
    is_mock: bool
```

`roc_auc_status` exists so `None` never means two different things at once — same reasoning as `RetrievedEvidence.evidence_status`.

**Exception contract:** the model layer raises `ProbabilityCapabilityUnavailable(Exception)` — a specific exception class — when `supports_probability` is `False` and an operation needs it. The orchestration layer catches this specific exception and maps it to `roc_auc_status = "unavailable_no_probabilities"`.

### B3. API-boundary validation

No new validator mechanism needed. Required-field-no-default is the entire validation story, matching this codebase's only existing "fail clearly" pattern (plain guard clauses, zero `@validator` decorators anywhere).

### B4. Run identity propagation

`build_assurance_result()` becomes the minting authority — generates one `assurance_run_id` at the top of the function, passes it explicitly into whichever `compute_real_*` calls produce envelope-wrapped results. Does **not** follow `ReportResult.report_id`'s per-call-minting pattern.

### B5. `feature_space` — derived, not separately constructed (resolved with Arushi)

`feature_space` is DERIVED from `DriftResult.features_evaluated`
(already exists, already reflects exactly what `drift_report()`
actually measured), not a separately-constructed value at the
orchestration layer. Proposal: a hash/fingerprint computed from
`features_evaluated`'s actual contents, so it is structurally
impossible for the envelope to claim a feature space that doesn't
match what drift actually evaluated. This resolves Arushi's concern
that orchestration simply constructing the value could silently
diverge from reality.

`dataset_id`/`dataset_version` remain flagged as depending on 5B/5C
work (per §B5's original note) — `compute_real_drift()` still
hardcodes its dataset import today.

### B6. `NOT_COMPARABLE` behavior — enforced, not advisory (resolved with Arushi)

New schema, patterned on the existing `RetrievedEvidence.evidence_status`
precedent:

```python
class DriftComparisonResult(BaseModel):
    comparability: Literal["COMPARABLE", "NOT_COMPARABLE"]
    reason: Optional[str] = None
    drift_a: DriftAssuranceEnvelope
    drift_b: DriftAssuranceEnvelope
```

Not a field on `DriftResult` (comparability is a property of a *pair*).
Not an HTTP error code (gives the dashboard nothing to render).

**Enforcement is structural, not advisory** (per Arushi's review): the
eventual comparison logic (5D/5F) must REFUSE to produce a normal
comparison result when required conditions fail — feature-space and
evaluated-feature-set checks are enforced by the comparison function
itself, not left to callers to interpret correctly. `NOT_COMPARABLE`
is the only valid outcome when those checks fail, not an optional flag
callers might skip checking.

**Scope note (unchanged):** the actual comparison endpoint/logic
belongs to 5D/5F, not 5A/5B — this section defines the shape and
enforcement requirement only, doesn't build the comparison now.

### B7. Downstream integration requirements (flagged, not built here)

- `app/report/generate.py`'s evidence routing needs to move from `evidence_type`-only to `(evidence_type, model_id)` once envelopes exist, to prevent Model A/B evidence interleaving — a pre-5D concern.
- Dashboard panels will need `model_id`/`assurance_run_id` displayed once multi-model exists — a 5F concern.
