# RBI MODEL ASSURANCE — DEMO REQUIREMENT SET

## PURPOSE

This is a curated RBI requirement set for the RBI Model Risk & Assurance Copilot.

The requirements are intended for a CREDIT-SCORING / LENDING MODEL assurance scenario.

IMPORTANT:

* This is a curated demonstration corpus, NOT complete RBI coverage.
* Every requirement must be mapped to a verified official RBI source before being treated as a live regulatory requirement.
* Preserve source URL, document ID, section/paragraph, publication date, updated date and regulatory status.
* Draft/advisory material must never be presented as a binding RBI requirement.
* Applicability must be evaluated before assessment.
* Missing evidence must result in NOT_ASSESSED, EVIDENCE_MISSING, NOT_FOUND or APPLICABILITY_UNCLEAR as appropriate.
* The LLM must NEVER determine compliance status.
* Compliance status must be produced by deterministic rules/evidence evaluation.
* The LLM may only explain verified findings and their regulatory basis.

RULE 01 — MODEL GOVERNANCE AND ACCOUNTABILITY
=============================================

requirement_id:
RBI-MODEL-GOV-001

title:
Model governance, accountability and oversight

source_family:
RBI model-risk / model-governance material

regulatory_status:
VERIFY_SOURCE_STATUS

applicability:
Applies to assessments where RBI model-risk/model-governance guidance is
applicable to the regulated entity and model use case.

requirement:
The regulated entity should maintain defined governance, accountability,
oversight and documented responsibilities for material models used in
credit or other regulated decision-making.

evidence_required:
- model owner
- model governance policy
- assigned responsibilities
- approval/oversight records
- model inventory entry
- governance committee or equivalent evidence

assessment_mode:
EVIDENCE_BASED

failure_condition:
Required governance evidence is missing or responsibilities are not
demonstrably assigned.

notes:
If the underlying RBI source is draft/advisory rather than binding,
classify it as advisory and do not present a failure as a statutory
violation.

============================================================
ASSESSMENT STATUS RULES
=======================

The platform must use the following principles:

## PASS

Use only when required evidence is available and satisfies the deterministic
assessment criteria.

## FAIL

Use only when applicable required evidence is available and demonstrably
fails the deterministic requirement.

## PARTIAL

Use when some required evidence is present but coverage is incomplete.

## EVIDENCE_MISSING

Use when the requirement appears applicable but required evidence was not
provided.

## NOT_ASSESSED

Use when there is insufficient information to perform the assessment.

## APPLICABILITY_UNCLEAR

Use when the available entity/model/context information is insufficient to
determine whether the requirement applies.

## NOT_APPLICABLE

Use only when applicability has been deterministically established as false.

IMPORTANT:
The absence of evidence must NOT automatically become PASS.
The absence of evidence must NOT automatically become FAIL unless the
assessment rule explicitly establishes that failure from the available
evidence.

MODEL-ASSURANCE EVIDENCE MAPPING
================================

The existing assurance platform may provide:

1. model_id
2. model_version
3. assurance_run_id
4. model type
5. adapter type
6. prediction evidence
7. SHAP explainability
8. LIME explainability
9. fairness metrics
10. feature drift metrics
11. prediction/output drift metrics
12. model provenance
13. integration provenance

These are PLATFORM ASSURANCE EVIDENCE.

They must NOT automatically be interpreted as proof of organizational,
contractual, governance, KYC, outsourcing, borrower-protection or other
regulatory controls.

Example:

SHAP available
!=
RBI model governance compliance proven

RESTAdapter available
!=
RBI outsourcing compliance proven

Fairness metric available
!=
RBI fairness compliance proven

Drift metric available
!=
RBI monitoring requirement automatically satisfied

The platform must distinguish:

* technical/model evidence
* organizational evidence
* contractual/vendor evidence
* regulatory evidence
* attestation-based evidence

============================================================
CORPUS PRINCIPLES
=================

1. This corpus is intentionally CURATED and PARTIAL.

2. Every production/live requirement must have:

   * official RBI source
   * document ID
   * official source URL
   * section/paragraph
   * publication date
   * latest verified update date
   * regulatory status
   * applicability condition

3. Historical or superseded RBI documents must not silently be treated as
   current requirements.

4. Draft guidance must be clearly labelled as DRAFT/ADVISORY.

5. Current applicability must be evaluated using the assessment context.

6. RBI requirements must be separated from internal platform thresholds.

7. The LLM is a NARRATIVE layer only.

8. The LLM must never:

   * invent an RBI requirement
   * determine PASS/FAIL
   * invent a citation
   * invent applicability
   * convert missing evidence into compliance
   * treat a draft as binding

9. The deterministic RBI engine is responsible for:

   * applicability
   * evidence matching
   * status
   * source provenance
   * requirement identifiers

10. Reports should clearly state that this is a curated demonstration
    corpus and does not represent complete RBI regulatory coverage.
